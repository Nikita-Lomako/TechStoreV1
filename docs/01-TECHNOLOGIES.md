# 01. Технологии, подходы и термины

Этот файл — словарь проекта. Для каждого пункта есть четыре ответа:

- **Что это** — определение простыми словами.
- **Зачем это** — какую проблему решает.
- **Как это работает здесь** — где именно в TechStore.
- **Альтернативы и почему выбрано это** — что могли взять вместо и почему текущий вариант удобнее.

Читать подряд не обязательно: можно использовать как справочник. Но перед защитой полезно пройтись по всем разделам.

## 1. Платформа и язык

### Node.js

- **Что это.** Среда выполнения JavaScript/TypeScript вне браузера. Построена на движке V8.
- **Зачем.** Позволяет писать backend на том же языке, что и frontend, и использовать огромную экосистему npm.
- **Как здесь.** API работает на Node.js 24 (образ `node:24-bookworm-slim`), запускает Fastify, Prisma, Redis-клиент и отправку писем. Frontend собирается Vite, который тоже работает на Node.js.
- **Альтернативы.** Deno и Bun — современные runtime, но у них меньше совместимость с Prisma/Fastify и корпоративными библиотеками; Python/Java backend потребовал бы второго языка. Node выбран как самый предсказуемый и распространённый вариант для учебного full-stack проекта.

### npm

- **Что это.** Менеджер пакетов и скриптов Node.js. Читает `package.json`, ставит зависимости в `node_modules`, создаёт lock-файл.
- **Зачем.** Воспроизводимо устанавливать одинаковые версии библиотек и запускать команды (`dev`, `build`, `test`).
- **Как здесь.** Два независимых пакета: корневой (`package.json` — фронтенд) и `server/package.json` (API). В Docker используется `npm ci` — установка строго по `package-lock.json`.
- **Альтернативы.** pnpm и Yarn быстрее и экономнее по диску, но npm уже установлен с Node и не требует дополнительных инструментов. Для учебного проекта важнее простота.

### TypeScript

- **Что это.** JavaScript с типами. Типы проверяются при компиляции и стираются в рантайме.
- **Зачем.** Ловит опечатки и несовместимые данные до запуска: например, если в функцию передали строку вместо числа. Улучшает автодополнение и документирует контракты.
- **Как здесь.** Весь сервер (`server/src/**/*.ts`) написан на TypeScript. `npm run typecheck` запускает `tsc --noEmit`, `npm run build` компилирует в `server/dist`. Frontend — JavaScript/JSX, потому что так был оформлен исходный учебный проект; код проверяется ESLint.
- **Альтернативы.** Чистый JavaScript проще стартовать, но в API много структур (продукт, корзина, токены), где ошибки дорого ловить в рантайме. Flow почти вышел из употребления. TypeScript — стандарт индустрии.

### ESM (`import` / `export`)

- **Что это.** Современный модульный формат JavaScript. В `package.json` включён `"type": "module"`.
- **Зачем.** Явные импорты, статический анализ, единый формат для фронтенда и бэкенда.
- **Как здесь.** Все серверные импорты имеют расширение `.js`, даже если исходник `.ts`: после компиляции TypeScript файлы становятся `.js`, и Node ищет именно их. Например, `import { prisma } from './lib/prisma.js'`.
- **Альтернативы.** CommonJS (`require`) — старый формат, всё ещё работает, но хуже сочетается с современными библиотеками и tree-shaking. Выбран ESM.

### Переменные окружения (environment variables)

- **Что это.** Параметры, которые передаются процессу снаружи, а не хранятся в коде: пароли, URL, секреты.
- **Зачем.** Один и тот же код работает локально, в Docker и на Render с разными настройками. Секреты не попадают в Git.
- **Как здесь.** `server/src/config/env.ts` читает `process.env`, проверяет через Zod и завершает процесс, если конфигурация неверна. Примеры лежат в `.env.example` и `server/.env.example`; реальные `.env` в `.gitignore`.
- **Альтернативы.** Конфиг-файлы в репозитории опасны утечкой секретов; хардкод не позволяет менять окружение. Env-переменные — стандарт 12-factor приложений.

### 12-factor app

- **Что это.** Набор принципов для приложений, которые легко деплоить: конфиг в окружении, stateless-процессы, логи в stdout, явные зависимости.
- **Зачем.** Приложение одинаково ведёт себя локально и в облаке, легко масштабируется и перезапускается.
- **Как здесь.** Секреты в env, API не хранит сессии в памяти (JWT + БД), логи пишутся в stdout (их собирает Docker/Render), зависимости зафиксированы lock-файлами.
- **Альтернативы.** «Толстые» серверы с локальными файлами и ручными настройками сложнее переносить и масштабировать.

## 2. Frontend

### React

- **Что это.** Библиотека для построения интерфейса из компонентов. Компонент — функция, которая возвращает JSX-описание UI.
- **Зачем.** Позволяет переиспользовать карточки, формы и страницы, а состояние интерфейса описывать декларативно.
- **Как здесь.** Весь UI — React 19. Корневой компонент `App` рендерит `AppRouterProvider`, страницы лежат в `src/pages`, переиспользуемые карточки — в `src/entities`.
- **Альтернативы.** Vue и Svelte тоже подходят, но React был в исходном фронтенде и имеет наибольшую экосистему. Angular тяжелее для небольшого проекта.

### React DOM и `createRoot`

- **Что это.** Пакет, который монтирует React-дерево в реальный DOM браузера.
- **Зачем.** React сам по себе не знает про браузер; `react-dom/client` связывает виртуальное дерево с элементом `#root`.
- **Как здесь.** `src/main.jsx` вызывает `createRoot(document.getElementById('root')).render(<App />)`.
- **Альтернативы.** Preact легче, но менее совместим с экосистемой; серверный рендеринг (Next.js) здесь не нужен, потому что приложение статическое и работает с API.

### JSX

- **Что это.** Синтаксис, похожий на HTML, внутри JavaScript. Vite/плагин React превращает его в вызовы `createElement`.
- **Зачем.** UI описывается декларативно и рядом с логикой компонента.
- **Как здесь.** Все `.jsx`-файлы: страницы, Header, ProductCard и т.д.
- **Альтернативы.** Шаблонные строки или отдельные HTML-шаблоны менее удобны и хуже типизируются.

### React Router

- **Что это.** Библиотека клиентской навигации: сопоставляет URL с компонентом без перезагрузки страницы.
- **Зачем.** SPA должна иметь разные адреса (`/cart`, `/product/:id`), кнопки «назад/вперёд» и прямые ссылки.
- **Как здесь.** `react-router-dom` 7. Маршруты описаны в `src/app/providers/router/AppRoutes.jsx`, константы — в `src/shared/config/routes.js`. Используется `HashRouter`.
- **Альтернативы.** TanStack Router даёт более строгую типизацию, но сложнее; Next.js Router требует серверного фреймворка. React Router — стандарт и уже был в проекте.

### HashRouter и почему не BrowserRouter

- **Что это.** Router, который хранит путь после `#`: `https://site/#/cart`.
- **Зачем.** GitHub Pages — статический хостинг. Он не умеет перенаправлять все пути на `index.html`, поэтому прямой заход на `/cart` дал бы 404. Hash-часть серверу не отправляется, и приложение само разбирает маршрут.
- **Как здесь.** `AppRouterProvider.jsx` оборачивает приложение в `HashRouter`. Плюс `base: './'` в `vite.config.js`, чтобы ассеты грузились из подпапки репозитория.
- **Альтернативы.** BrowserRouter + настройка fallback на Netlify/Vercel/Nginx; или `404.html`-трюк. HashRouter выбран как самый надёжный для GitHub Pages без сервера.

### Vite

- **Что это.** Сборщик и dev-сервер для фронтенда. Использует нативные ES-модули в разработке и Rollup для production-сборки.
- **Зачем.** Мгновенный старт, горячая замена модулей (HMR), минификация, хэширование файлов, поддержка `import.meta.env`.
- **Как здесь.** `npm run dev` поднимает `http://localhost:5173`; `npm run build` создаёт `dist/`; `VITE_API_URL` встраивается в бандл на этапе сборки.
- **Альтернативы.** Webpack гибче, но медленнее и требует больше конфигурации; CRA устарел. Vite — современный стандарт для React SPA.

### `import.meta.env.VITE_*`

- **Что это.** Механизм Vite передавать переменные окружения в клиентский код.
- **Зачем.** Фронтенд должен знать адрес API, но не должен знать секреты.
- **Как здесь.** `src/shared/api/client.js`: `import.meta.env.VITE_API_URL` или `http://localhost:3000` по умолчанию. В клиент попадают **только** переменные с префиксом `VITE_`.
- **Альтернативы.** Runtime-конфиг через `/config.json` позволяет менять адрес без пересборки, но усложняет деплой. Для статического GitHub Pages build-time переменная проще.

### Feature-Sliced Design (FSD)

- **Что это.** Архитектурный подход к фронтенду: код делится на слои `app → pages → widgets → features → entities → shared`, зависимости идут только «вниз».
- **Зачем.** Когда компонентов много, папка «components» превращается в свалку. FSD даёт предсказуемое место для каждой сущности и уменьшает связность.
- **Как здесь.** `src/app` — провайдеры и роутер; `src/pages` — страницы; `src/widgets` — Header/Footer; `src/features` — auth и cart; `src/entities` — ProductCard/ProductRating; `src/shared` — API, конфиги, хуки.
- **Альтернативы.** Группировка по файлам (`components/`, `hooks/`, `utils/`) проще на старте, но хуже масштабируется. Модульная структура по доменам — близкий вариант; FSD выбрана как более формальная.

### Context API

- **Что это.** Встроенный в React механизм передавать данные вниз по дереву без «prop drilling».
- **Зачем.** Корзина и текущий пользователь нужны во многих местах (Header, страницы, карточки). Передавать их через пропсы на каждом уровне неудобно.
- **Как здесь.** `AuthContext` и `CartContext` создаются отдельно (`auth-context.js`, `cart-context.js`), а провайдеры (`AuthProvider`, `CartProvider`) наполняют их значением. Хуки `useAuth`/`useCart` читают контекст.
- **Альтернативы.** Redux Toolkit и Zustand мощнее для сложного состояния, но добавляют зависимости и церемонии. Для двух доменов достаточно Context. Если состояние станет сложным (заказы, фильтры, десятки экранов), стоит перейти на Zustand/Redux.

### Provider composition

- **Что это.** Паттерн, когда провайдеры вкладываются друг в друга, образуя дерево зависимостей.
- **Зачем.** `CartProvider` использует `useAuth`, поэтому обязан находиться **внутри** `AuthProvider`.
- **Как здесь.** `HashRouter → AuthProvider → CartProvider → AppRoutes`. Порядок важен: если поменять местами auth и cart, `useAuth()` в корзине вернёт `undefined`.
- **Альтернативы.** Один «мега-провайдер» скрывает зависимости и хуже тестируется. Явная композиция понятнее.

### Кастомные хуки

- **Что это.** Функции, начинающиеся с `use`, которые переиспользуют логику состояния/эффектов.
- **Зачем.** Убрать дублирование и отделить поведение от разметки.
- **Как здесь.** `useAuth`, `useCart`, `useDebouncedValue`. Хуки контекста лежат в `features/*/index.js`.
- **Альтернативы.** HOC и render props — старые паттерны, более громоздкие. Хуки — современный стандарт React.

### `useState`, `useEffect`, `useMemo`, `useCallback`, `useRef`

- **Что это.** Базовые хуки React.
  - `useState` — локальное состояние.
  - `useEffect` — побочный эффект после рендера (запрос, подписка).
  - `useMemo` — мемоизация вычисленного значения.
  - `useCallback` — стабильная ссылка на функцию.
  - `useRef` — изменяемое значение, не вызывающее рендер.
- **Зачем.** Управлять жизненным циклом UI и не делать лишнюю работу.
- **Как здесь.**
  - `CatalogPage` хранит фильтры и результаты в `useState`, делает запрос в `useEffect`.
  - `CartProvider` хранит `mutationQueue` в `useRef`, чтобы очередь запросов не вызывала рендер.
  - `useMemo` собирает `lines` и `totals`, чтобы не пересчитывать их на каждом рендере.
- **Альтернативы.** Классовые компоненты устарели; внешние стейт-менеджеры не нужны для локального UI.

### Debounce

- **Что это.** Задержка выполнения действия до паузы во вводе.
- **Зачем.** Без него каждый символ в поиске отправлял бы запрос к API.
- **Как здесь.** `useDebouncedValue(search, 350)` и задержка 400 мс для ползунков цены. Запрос уходит только после паузы.
- **Альтернативы.** Throttle ограничивает частоту, но всё равно шлёт промежуточные запросы. Debounce лучше для поиска.

### AbortController

- **Что это.** Стандартный способ отменить `fetch`.
- **Зачем.** Если пользователь быстро меняет фильтры или уходит со страницы, старый запрос не должен перезаписать новые данные.
- **Как здесь.** В `CatalogPage` и `ProductPage` создаётся `AbortController`, в cleanup эффекта вызывается `abort()`. В `client.js` ошибка `AbortError` пробрасывается отдельно, чтобы её не показывали как ошибку сети.
- **Альтернативы.** Флаги `cancelled` без отмены запроса: запрос всё равно выполняется и тратит ресурсы. AbortController эффективнее.

### `localStorage`

- **Что это.** Key-value хранилище в браузере, сохраняется между перезагрузками.
- **Зачем.** Гостевая корзина и токены должны пережить закрытие вкладки.
- **Как здесь.** `cartPersistence.js` хранит гостевые позиции и промокод; `client.js` — access/refresh токены. Все обращения обёрнуты в `try/catch`, потому что в приватном режиме или при переполнении хранилище может быть недоступно.
- **Альтернативы.** `sessionStorage` живёт до закрытия вкладки; cookies автоматически отправляются, но с JWT это создаёт CSRF-риски. `localStorage` выбран для явного `Authorization`-заголовка. Подробнее о рисках — в `04-SECURITY.md`.

### Intl.NumberFormat

- **Что это.** Встроенный API форматирования чисел, валют и дат.
- **Зачем.** Показывать цену как `$1,299.00`, а не `1299`.
- **Как здесь.** `formatPrice` в `CartPage`, `ProductPage`, `AdminProductsPage`.
- **Альтернативы.** Ручное форматирование или библиотека `dinero.js`; для одной валюты встроенного API достаточно.

## 3. Backend

### Fastify

- **Что это.** Веб-фреймворк для Node.js с акцентом на скорость, плагины и схему запросов.
- **Зачем.** Нужен HTTP-сервер, маршруты, валидация, сериализация, логирование и Swagger.
- **Как здесь.** `buildApp()` в `server/src/app.ts` создаёт экземпляр, регистрирует CORS, Helmet, rate-limit, JWT, multipart, Swagger. Модули подключаются как плагины в `routes.ts`.
- **Альтернативы.** Express — самый популярный, но валидацию и Swagger нужно собирать вручную; NestJS — мощный, но тяжёлый и многословный для учебного API. Fastify даёт схему, скорость и хорошую структуру «из коробки».

### Плагины Fastify

- **Что это.** Функции, которые расширяют приложение и могут иметь собственный scope.
- **Зачем.** Каждый модуль (`auth`, `products`, `cart`) регистрируется отдельно и не засоряет общий файл.
- **Как здесь.** `app.register(authRoutes)`, `productRoutes`, `cartRoutes`, `uploadRoutes`, `healthRoutes` в `routes.ts`.
- **Альтернативы.** Один большой файл маршрутов; монолитный роутер сложнее поддерживать. Плагины дают изоляцию и переиспользование.

### Хуки жизненного цикла (`onClose`, `preHandler`)

- **Что это.** Точки, куда можно вставить код до/после обработчика или при завершении приложения.
- **Зачем.** Проверять авторизацию до бизнес-логики и корректно закрывать ресурсы.
- **Как здесь.** `preHandler: authenticate`/`requireAdmin` защищает маршруты; `app.addHook('onClose', ...)` отключает Prisma и Redis.
- **Альтернативы.** Ручные проверки внутри каждого обработчика — дублирование и риск забыть. Хуки централизуют поведение.

### TypeBox

- **Что это.** Библиотека описания схем на TypeScript, которая генерирует JSON Schema и выводит статические типы через `Static<typeof Schema>`.
- **Зачем.** Одна схема используется для валидации запроса, сериализации ответа, типов TypeScript и Swagger.
- **Как здесь.** `schemas.ts` в каждом модуле: `ProductSchema`, `CartResponseSchema`, `RegisterBodySchema`. В `app.ts` подключён `TypeBoxTypeProvider`, поэтому `request.body` типизирован.
- **Альтернативы.** Zod удобен для runtime-валидации, но Fastify/Swagger нативно работают с JSON Schema; TypeBox даёт и то, и другое без конвертации. Zod в проекте используется только для env, где не нужен Swagger.

### Zod

- **Что это.** TypeScript-библиотека валидации с выводом типов.
- **Зачем.** Проверить переменные окружения один раз при старте и получить понятные ошибки.
- **Как здесь.** `server/src/config/env.ts`: `envSchema.safeParse(process.env)`, проверка `JWT_SECRET` минимум 16 символов, портов, TTL и т.д.
- **Альтернативы.** Joi, Yup, ручные проверки. Zod компактнее и лучше типизируется.

### JSON Schema / OpenAPI 3 / Swagger UI

- **Что это.** JSON Schema описывает форму данных; OpenAPI — стандарт описания REST API; Swagger UI рисует интерактивную документацию.
- **Зачем.** Клиент и проверяющий видят все эндпоинты, параметры, ответы и могут делать запросы из браузера.
- **Как здесь.** `@fastify/swagger` собирает OpenAPI из схем маршрутов, `@fastify/swagger-ui` отдаёт `/docs`, JSON — `/docs/json`. Схемы ответов одновременно являются сериализаторами.
- **Альтернативы.** Postman-коллекции и ручные markdown-документы устаревают; генерация из кода всегда соответствует реальности.

### Валидация на границе

- **Что это.** Подход: проверять все внешние данные (body, query, params) до бизнес-логики.
- **Зачем.** Внутренний код может доверять типам и не проверять одно и то же десять раз.
- **Как здесь.** Схемы Fastify автоматически возвращают `400 VALIDATION_ERROR` с путём и сообщением. Например, `images` требует минимум 3 элемента, `quantity` — от 1 до 99.
- **Альтернативы.** Проверки внутри сервисов размазывают ответственность; валидация на границе чище.

### Сериализация ответа схемой

- **Что это.** Fastify пропускает ответ через JSON Schema и оставляет только описанные поля.
- **Зачем.** Случайно не отдать `passwordHash`, `deletedAt` или внутренние поля; заодно ускорить сериализацию.
- **Как здесь.** У каждого маршрута есть `response: { 200: ... }`. Например, `UserSchema` содержит только `id`, `email`, `role`, `createdAt`.
- **Альтернативы.** Ручное `delete user.passwordHash` легко забыть. Схема — декларативный «белый список».

### JWT (JSON Web Token)

- **Что это.** Подписанный токен из трёх частей: заголовок, payload, подпись. Сервер проверяет подпись секретом и доверяет payload.
- **Зачем.** Не хранить сессию в памяти и не ходить в БД на каждый запрос.
- **Как здесь.** `@fastify/jwt`, payload `{ sub, email, role }`, срок 15 минут (`JWT_EXPIRES_IN`). Клиент присылает `Authorization: Bearer <token>`.
- **Альтернативы.** Серверные сессии в Redis/БД проще отзывать, но требуют хранилища и запроса на каждый запрос. JWT удобен для отдельного API и горизонтального масштабирования. Минус — отзыв access-токена до истечения невозможен, поэтому срок короткий.

### Access token и refresh token

- **Что это.** Пара токенов: короткий access для запросов и долгий refresh для получения нового access.
- **Зачем.** Кража access-токена ограничена 15 минутами, а refresh можно отозвать и ротировать.
- **Как здесь.** Access — JWT на 15 минут. Refresh — случайные 32 байта (`randomBytes(32).toString('base64url')`), в БД хранится SHA-256 хэш, срок 7 дней. При `/api/auth/refresh` старый refresh помечается revoked, создаётся новый (ротация).
- **Альтернативы.** Один долгий JWT проще, но опаснее; только серверные сессии надёжнее для отзыва, но тяжелее. Пара токенов — компромисс.

### RBAC (Role-Based Access Control)

- **Что это.** Доступ по ролям, а не по конкретным пользователям.
- **Зачем.** `admin` может управлять товарами, `customer` — только смотреть каталог и свою корзину.
- **Как здесь.** Enum `Role` в Prisma, `request.user.role`, `requireAdmin` на маршрутах создания/изменения/удаления товара и загрузки. На фронтенде `RequireAuth adminOnly` скрывает страницу, но сервер проверяет независимо.
- **Альтернативы.** ACL на каждого пользователя избыточен; ABAC (по атрибутам) сложнее. Для двух ролей RBAC идеален.

### bcrypt / bcryptjs

- **Что это.** Алгоритм хэширования паролей с солью и настраиваемой «стоимостью» (количеством раундов).
- **Зачем.** Пароль нельзя хранить открытым; хэш должен быть медленным, чтобы перебор был дорогим.
- **Как здесь.** `bcryptjs`, 12 раундов (`BCRYPT_ROUNDS`). При регистрации `bcrypt.hash`, при входе `bcrypt.compare`. В seed пароли тоже хэшируются.
- **Альтернативы.** Argon2id считается современнее и устойчивее к GPU, но требует нативной сборки; bcryptjs — чистый JS, работает везде без компиляции. Для учебного проекта важна переносимость. PBKDF2 слабее против GPU.

### Хэш и соль

- **Что это.** Хэш — необратимое преобразование; соль — случайные данные, добавляемые к паролю, чтобы одинаковые пароли давали разные хэши.
- **Зачем.** Защита от радужных таблиц и утечки «одинаковых» паролей.
- **Как здесь.** bcrypt сам генерирует соль и хранит её внутри строки хэша.
- **Альтернативы.** MD5/SHA-1 без соли категорически нельзя. bcrypt/argon2 — правильный выбор.

### SHA-256 для токенов

- **Что это.** Быстрая криптографическая хэш-функция.
- **Зачем.** Refresh/reset-токены имеют высокую энтропию, поэтому их можно хранить в виде SHA-256, а не bcrypt: даже при утечке БД восстановить токен нельзя, а проверка остаётся быстрой.
- **Как здесь.** `lib/tokens.ts`: `hashToken` возвращает hex SHA-256; в БД `token_hash` уникален.
- **Альтернативы.** bcrypt для токенов был бы медленным и не давал бы преимущества при 256-битной случайности. HMAC с секретом тоже возможен, но SHA-256 достаточно.

### Opaque token

- **Что это.** Токен без полезной нагрузки — просто случайная строка, смысл которой знает только сервер (через запись в БД).
- **Зачем.** Не раскрывает данные пользователя и легко отзывается.
- **Как здесь.** Refresh и reset-токены — opaque, создаются `randomBytes(32)`.
- **Альтернативы.** JWT для refresh тоже возможен, но тогда сложнее мгновенный отзыв и ротация.

### CORS

- **Что это.** Механизм браузера, который разрешает или запрещает кросс-доменные запросы к API.
- **Зачем.** Фронтенд на `github.io` и API на `onrender.com` — разные origin. Без заголовков `Access-Control-Allow-*` браузер заблокирует ответ.
- **Как здесь.** `@fastify/cors` с allowlist из `CORS_ORIGINS`, поддержкой wildcard-поддоменов, `credentials: false`, разрешёнными заголовками `Content-Type`, `Authorization`, экспортом `X-Cache`, `X-Cache-TTL`.
- **Альтернативы.** `origin: true` разрешает всем — небезопасно. Проксирование через тот же домен убирает CORS, но добавляет сервер. Allowlist — стандарт.

### Helmet

- **Что это.** Набор middleware, который выставляет защитные HTTP-заголовки.
- **Зачем.** Уменьшает риск кликджекинга, MIME-sniffing, утечки referrer.
- **Как здесь.** `@fastify/helmet`: CSP отключён (Swagger UI использует inline-скрипты), `crossOriginResourcePolicy: cross-origin`, `referrerPolicy: no-referrer`.
- **Альтернативы.** Ручная установка заголовков; Helmet покрывает стандартные случаи. Отключение CSP — осознанный компромисс ради `/docs`; в проде без Swagger CSP можно включить.

### Rate limiting

- **Что это.** Ограничение числа запросов с одного IP/ключа за время.
- **Зачем.** Защита от перебора паролей, спама и случайной перегрузки.
- **Как здесь.** `@fastify/rate-limit`: глобально 200 запросов/мин, для auth — отдельные лимиты (регистрация 5/15 мин, вход 10/15 мин, refresh 30/15 мин, forgot 5/15 мин).
- **Альтернативы.** WAF/Cloudflare на уровне инфраструктуры, но приложению всё равно нужны свои лимиты. In-memory лимитер не разделяется между инстансами; для нескольких реплик нужен Redis-store (в проекте не настроен).

### Multipart / `@fastify/multipart`

- **Что это.** Разбор `multipart/form-data` — формата загрузки файлов.
- **Зачем.** Админ должен загружать картинки, а не только вставлять URL.
- **Как здесь.** Лимит 1 файл, 5 МБ, поле `file`; MIME проверяется по allowlist (JPEG, PNG, WebP, AVIF, GIF). Файл читается в буфер и отправляется в Supabase Storage.
- **Альтернативы.** Base64 в JSON раздувает тело на ~33%; прямая загрузка с клиента в Supabase потребовала бы отдавать service-role key браузеру (нельзя). Серверный proxy безопаснее.

### pino

- **Что это.** Быстрый JSON-логгер, встроенный в Fastify.
- **Зачем.** Структурные логи легко читать машиной и искать по полям.
- **Как здесь.** В development — `pino-pretty` с цветами и временем; в production — обычный JSON в stdout; в тестах логи отключены. Уровень задаётся `LOG_LEVEL`.
- **Альтернативы.** Winston, console.log. Pino быстрее и уже интегрирован с Fastify (автоматические request-логи).

### nodemailer

- **Что это.** Библиотека отправки email по SMTP.
- **Зачем.** Ссылка сброса пароля должна приходить на почту.
- **Как здесь.** `lib/mailer.ts` создаёт transporter лениво. Если `SMTP_HOST` пуст, письмо не отправляется, а ссылка пишется в лог (удобно локально).
- **Альтернативы.** SendGrid/Resend API — надёжнее для продакшена, но требуют аккаунта и ключа. SMTP универсален.

## 4. Данные

### PostgreSQL

- **Что это.** Реляционная СУБД с транзакциями, внешними ключами, индексами, JSONB, массивами.
- **Зачем.** Магазину нужны строгие связи (пользователь → корзина → позиции → товар) и гарантии целостности.
- **Как здесь.** PostgreSQL 16 в Docker, Supabase в облаке. Таблицы `users`, `products`, `carts`, `cart_items`, `promo_codes`, `refresh_tokens`, `password_reset_tokens`.
- **Альтернативы.** MongoDB гибче по схеме, но не даёт таких удобных связей и транзакционной целостности; MySQL ближе, но PostgreSQL богаче типами (массивы, JSONB, GIN/trgm). Supabase предоставляет именно PostgreSQL.

### Prisma ORM

- **Что это.** ORM и инструмент миграций: схема на DSL, генерация типизированного клиента, миграции, studio.
- **Зачем.** Не писать SQL вручную для CRUD, получать типы и автодополнение, версионировать схему.
- **Как здесь.** `server/prisma/schema.prisma` описывает модели; `prisma migrate` создаёт SQL; `prisma generate` — клиент; `prisma/seed.js` наполняет БД.
- **Альтернативы.** Drizzle легче и ближе к SQL; TypeORM популярен, но исторически нестабилен; raw SQL даёт максимум контроля, но больше рутины. Prisma выбрана за типобезопасность и понятные миграции. Для агрегата категорий используется `$queryRaw` — это нормальный «escape hatch».

### Prisma Client

- **Что это.** Сгенерированный клиент с методами `findMany`, `create`, `update`, `upsert`, `$transaction`.
- **Зачем.** Типизированные запросы вместо строк SQL.
- **Как здесь.** `lib/prisma.ts` создаёт singleton. В development он кладётся в `globalThis`, чтобы горячая перезагрузка `tsx watch` не открывала новые пулы соединений.
- **Альтернативы.** Новый `PrismaClient()` в каждом модуле исчерпает соединения. Singleton — стандарт.

### Миграции

- **Что это.** Файлы с изменениями схемы БД, применяемые по порядку.
- **Зачем.** Схема развивается вместе с кодом, и на любом окружении её можно привести к нужному состоянию.
- **Как здесь.** `server/prisma/migrations/20261013090000_init/migration.sql`. Локально `prisma migrate dev`, в Docker/Render `prisma migrate deploy`.
- **Альтернативы.** `db push` без истории быстрее, но не подходит для продакшена. Миграции — воспроизводимость.

### Seed

- **Что это.** Скрипт наполнения БД начальными данными.
- **Зачем.** Чтобы после `docker compose up` сразу были товары, пользователи и промокоды.
- **Как здесь.** `prisma/seed.js` + `seed-data.js`: 12 товаров, admin/customer, SAVE10/WELCOME5. Используется `upsert`, поэтому повторный запуск не создаёт дубликаты.
- **Альтернативы.** Ручное заполнение через админку/psql медленно и не воспроизводимо.

### UUID

- **Что это.** 128-битный идентификатор, практически уникальный без координации.
- **Зачем.** Не раскрывать количество записей (в отличие от `1, 2, 3`) и безопасно генерировать id на клиенте/сервере.
- **Как здесь.** `@default(uuid()) @db.Uuid` у всех основных моделей.
- **Альтернативы.** Auto-increment проще и компактнее, но предсказуем и хуже для распределённых систем. UUID выбран как безопаснее.

### `Decimal(10,2)`

- **Что это.** Точный десятичный тип для денег.
- **Зачем.** Float может дать `19.990000000000002`; деньги так считать нельзя.
- **Как здесь.** `Product.price Decimal @db.Decimal(10, 2)`, в DTO преобразуется в `Number` для JSON, а расчёты округляются функцией `roundMoney`.
- **Альтернативы.** Хранить центы целым числом — самый строгий вариант; Decimal достаточно и удобнее для чтения. Float для денег — ошибка.

### JSONB

- **Что это.** Бинарный JSON в PostgreSQL, индексируемый и эффективный.
- **Зачем.** Характеристики товара (`highlights`) могут быть разной формы.
- **Как здесь.** `Product.highlights Json?` хранит массив `{ label, value }`.
- **Альтернативы.** Отдельная таблица `product_highlights` строже, но для простого списка пар «ключ-значение» избыточна.

### Массивы PostgreSQL

- **Что это.** Колонка, хранящая массив значений (например, URL картинок).
- **Зачем.** У товара от 3 до 12 изображений; отдельная таблица усложнила бы CRUD.
- **Как здесь.** `Product.images String[]`. В API отдаётся и `images`, и `image` (первая).
- **Альтернативы.** Таблица `product_images` правильнее при сложной работе с изображениями (порядок, метаданные, удаление). Для учебного проекта массив проще.

### Нормализация и денормализация

- **Что это.** Нормализация убирает дублирование данных; денормализация осознанно добавляет избыточность ради скорости/простоты.
- **Зачем.** Баланс между целостностью и производительностью.
- **Как здесь.** Основные связи нормализованы (корзина ссылается на товар по `product_id`). При этом `image` в DTO вычисляется из массива, а `Product` хранит `category` строкой, а не отдельной таблицей.
- **Альтернативы.** Полностью нормализованная схема с `categories` и `product_images` строже, но требует больше join'ов и кода. Для каталога учебного масштаба текущая схема достаточна.

### Внешние ключи (FK)

- **Что это.** Ограничение, что значение ссылается на существующую строку другой таблицы.
- **Зачем.** Не оставить корзину с несуществующим товаром.
- **Как здесь.** `cart_items.cart_id → carts.id ON DELETE CASCADE`, `cart_items.product_id → products.id ON DELETE RESTRICT`, `carts.user_id → users.id CASCADE`.
- **Альтернативы.** Проверки только в коде ненадёжны: любой скрипт может нарушить целостность. FK — гарантия на уровне БД.

### Транзакции

- **Что это.** Группа операций, которая применяется целиком или не применяется вовсе (ACID).
- **Зачем.** Не оставить данные в полусостоянии.
- **Как здесь.** `prisma.$transaction` при удалении товара (удалить позиции корзины + soft-delete), при выдаче refresh-токена, при сбросе пароля (обновить пароль + погасить токен + отозвать сессии).
- **Альтернативы.** Последовательные запросы без транзакции могут упасть посередине. Транзакция — обязательна для связанных изменений.

### Индексы

- **Что это.** Структура, ускоряющая поиск по колонке, но замедляющая запись.
- **Зачем.** Фильтры и сортировка каталога не должны сканировать всю таблицу.
- **Как здесь.** B-tree по `price`, `rating`, `category`, `deleted_at`, `created_at`; уникальные по `email`, `token_hash`; составной уникальный `(cart_id, product_id)`.
- **Альтернативы.** Без индексов запросы медленнее; слишком много индексов замедляет вставку. Индексы добавлены под реальные фильтры.

### GIN и `pg_trgm`

- **Что это.** GIN — тип индекса для поиска по вхождениям; `pg_trgm` разбивает строки на триграммы, ускоряя `ILIKE '%текст%'`.
- **Зачем.** Поиск по названию и описанию должен работать быстро.
- **Как здесь.** Миграция включает `CREATE EXTENSION pg_trgm` и создаёт GIN-индексы на `title` и `description`. Prisma-запрос использует `contains` + `mode: 'insensitive'`, что превращается в `ILIKE`.
- **Альтернативы.** Полнотекстовый поиск (`tsvector`) точнее для языков, но сложнее в настройке; trigram-поиск проще и хорошо работает для подстрок. Для `longDescription` отдельного GIN-индекса нет — это известное ограничение.

### Пагинация offset (`skip`/`take`)

- **Что это.** Пропустить `(page - 1) * limit` строк и взять `limit`.
- **Зачем.** Не отдавать весь каталог сразу.
- **Как здесь.** `listProducts` делает `count` и `findMany` в одной транзакции, возвращает `meta.total_items`, `total_pages`, `current_page`, `limit`.
- **Альтернативы.** Cursor-пагинация стабильнее на больших данных и при частых вставках, но сложнее для UI с номерами страниц. Offset выбран из-за требований ТЗ.

### N+1 проблема

- **Что это.** Когда для списка из N элементов делают N дополнительных запросов.
- **Зачем.** Избегать лишних round-trip к БД.
- **Как здесь.** В корзине используется `include: { product: true }`, то есть товары загружаются join'ом, а не отдельным запросом на каждую позицию. В каталоге товары не имеют связанных таблиц, поэтому проблемы нет.
- **Альтернативы.** `select` только нужных полей и `include` связей; ручная сборка батчами. Prisma `include` решает типичный N+1.

### Пул соединений и PgBouncer

- **Что это.** Пул переиспользует открытые соединения к БД; PgBouncer — внешний пулер.
- **Зачем.** Открывать соединение на каждый запрос дорого; serverless/облако ограничивает их число.
- **Как здесь.** Prisma держит пул. Для Supabase в `.env.example` показан pooler на порту 6543 с `pgbouncer=true&connection_limit=1`, а `DIRECT_URL` на 5432 — для миграций.
- **Альтернативы.** Прямое подключение проще, но может исчерпать лимит Supabase. Pooler обязателен для продакшена.

## 5. Кэширование

### Redis

- **Что это.** In-memory key-value хранилище с TTL, атомарными операциями и сетью.
- **Зачем.** Быстро отдавать часто запрашиваемые данные, разделяя кэш между инстансами API.
- **Как здесь.** `ioredis` подключается к `REDIS_URL`; кэшируются списки товаров, карточки, related и категории; TTL 90 секунд.
- **Альтернативы.** In-memory Map быстрее, но не разделяется между процессами и теряется при рестарте; Memcached проще, но менее универсален. Redis — стандарт и поддерживает TTL/SCAN.

### Cache-aside (lazy caching)

- **Что это.** Паттерн: сначала читаем кэш; при промахе идём в БД и кладём результат в кэш.
- **Зачем.** Простая реализация и кэшируются только реально запрошенные данные.
- **Как здесь.** В маршрутах: `cache.get` → если есть, `X-Cache: HIT`; иначе сервис → `cache.set` → `X-Cache: MISS`.
- **Альтернативы.** Write-through обновляет кэш при каждой записи, но сложнее и может кэшировать лишнее. Cache-aside — самый распространённый.

### TTL

- **Что это.** Время жизни записи, после которого она исчезает.
- **Зачем.** Даже если инвалидация не сработала, данные не будут устаревшими вечно.
- **Как здесь.** `REDIS_TTL_SECONDS` по умолчанию 90 (по ТЗ 60–120). `SET key value EX ttl`.
- **Альтернативы.** Кэш без TTL опасен: изменения могут не дойти. TTL — страховка.

### Инвалидация по префиксу

- **Что это.** Удаление всех ключей, начинающихся с `products:`.
- **Зачем.** Один изменённый товар влияет на список, карточку, related и категории; проще снести всё пространство каталога.
- **Как здесь.** `cache.deleteByPrefix('products:')` после create/update/delete. Внутри Redis используется `SCAN MATCH`, а не `KEYS` (последний блокирует сервер на больших базах).
- **Альтернативы.** Точечное удаление ключей экономнее, но требует знать все варианты query-строк; риск пропустить. Префиксная инвалидация надёжнее для небольшого каталога.

### Нормализация ключа кэша

- **Что это.** Приведение query-параметров к каноническому виду перед хэшированием.
- **Зачем.** `?search=Laptop` и `?search=%20laptop%20` должны давать один ключ, иначе кэш будет дублироваться.
- **Как здесь.** `normalizeProductQuery` обрезает пробелы, приводит к нижнему регистру, подставляет значения по умолчанию; затем `URLSearchParams` + SHA-256 → `products:list:v1:<hash>`.
- **Альтернативы.** Ключ из сырой строки запроса даёт дубликаты; хранить объект в ключе нельзя. Нормализация + хэш — практичный вариант.

### In-memory fallback

- **Что это.** Запасной кэш в памяти процесса, если Redis недоступен.
- **Зачем.** Локальная разработка и тесты не должны требовать Redis; API не падает при кратком сбое.
- **Как здесь.** `CacheStore` всегда пишет в `Map` и дополнительно в Redis, если тот готов. При ошибке Redis переключается на память. `backend` возвращает `redis` или `memory`.
- **Альтернативы.** Жёстко требовать Redis — надёжнее для консистентности, но хуже для старта. Fallback удобен, но в production несколько инстансов будут иметь разные кэши — поэтому Redis обязателен.

## 6. Инфраструктура и деплой

### Docker

- **Что это.** Контейнеризация: приложение упаковывается вместе с зависимостями и настройками.
- **Зачем.** «Работает у меня» превращается в «работает везде»; Render запускает именно образ.
- **Как здесь.** `server/Dockerfile` — multi-stage; `docker-compose.yml` поднимает app + postgres + redis.
- **Альтернативы.** Виртуальные машины тяжелее; ручная установка Node/Postgres на сервере воспроизводится хуже. Docker — стандарт.

### Multi-stage build

- **Что это.** Несколько `FROM` в одном Dockerfile: сборка, установка production-зависимостей, финальный runtime.
- **Зачем.** В финальный образ не попадают dev-зависимости, исходники и компилятор TypeScript — образ меньше и безопаснее.
- **Как здесь.** `base → deps → build → prod-deps → runtime`. В runtime копируются `dist`, `node_modules`, Prisma-схема/миграции, `public`, entrypoint.
- **Альтернативы.** Один этап проще, но образ больше и содержит лишние инструменты. Multi-stage — best practice.

### Non-root пользователь

- **Что это.** Процесс в контейнере работает не от `root`, а от `node`.
- **Зачем.** Если приложение скомпрометируют, ущерб внутри контейнера меньше.
- **Как здесь.** `USER node` перед запуском; файлы скопированы с `--chown=node:node`.
- **Альтернативы.** Root по умолчанию удобнее, но опаснее. Non-root — базовое требование безопасности.

### Healthcheck

- **Что это.** Команда, которая проверяет, жив ли контейнер.
- **Зачем.** Docker/Render могут перезапустить зависший сервис и не отправлять трафик в неготовый инстанс.
- **Как здесь.** В Dockerfile — HTTP-запрос к `/health/live`; в Compose — `pg_isready` и `redis-cli ping`; Render health check path `/health/live`.
- **Альтернативы.** Проверка порта (`nc`) не говорит, что приложение реально отвечает. HTTP-healthcheck точнее.

### Docker Compose

- **Что это.** Инструмент описания нескольких контейнеров и их связей в YAML.
- **Зачем.** Одной командой поднять API, PostgreSQL и Redis с правильной сетью и зависимостями.
- **Как здесь.** `depends_on` с `condition: service_healthy`, named volumes, env_file, проброс портов.
- **Альтернативы.** Kubernetes мощнее, но избыточен; ручной `docker run` для трёх контейнеров неудобен. Compose — идеален для локальной разработки и учебного деплоя.

### Named volumes

- **Что это.** Docker-том с именем, который переживает пересоздание контейнера.
- **Зачем.** Данные PostgreSQL и Redis не должны исчезать при `docker compose down`.
- **Как здесь.** `techstore_postgres_data`, `techstore_redis_data`.
- **Альтернативы.** Bind mount на папку хоста удобнее для отладки, но зависит от прав и пути. Named volume — переносимее.

### Supabase

- **Что это.** Платформа на PostgreSQL + Auth + Storage + Realtime.
- **Зачем.** Managed-база и объектное хранилище без администрирования сервера.
- **Как здесь.** PostgreSQL используется через Prisma; Storage — для картинок товаров. Supabase Auth не используется: JWT-аутентификация своя.
- **Альтернативы.** Railway/Render Postgres + S3/Cloudinary; Supabase удобен тем, что даёт БД и Storage в одном месте с бесплатным тарифом. Минус — проект на free tier может «засыпать».

### Supabase Storage

- **Что это.** S3-подобное хранилище файлов с публичными/приватными bucket.
- **Зачем.** Не хранить бинарные картинки в PostgreSQL и не раздавать их с API.
- **Как здесь.** Bucket `product-images` публичный; API загружает файл через REST с `SUPABASE_SERVICE_ROLE_KEY`, возвращает публичный URL.
- **Альтернативы.** S3/Cloudflare R2/Cloudinary. Supabase выбран за единый аккаунт с БД. Публичный bucket означает, что картинки доступны всем по ссылке — для товаров это нормально.

### Render

- **Что это.** PaaS для запуска Docker-контейнеров и сервисов.
- **Зачем.** Не администрировать сервер, получить HTTPS, логи, health checks и деплой из GitHub.
- **Как здесь.** Инструкция в `06-DEPLOYMENT.md`: Language Docker, Root Directory `server`, Dockerfile Path `Dockerfile`, health `/health/live`, env из `server/.env.example`. `PORT` задаёт сам Render.
- **Альтернативы.** Railway, Fly.io, Heroku, Koyeb. Render поддерживает Docker и имеет бесплатный тариф; выбор учебный. Минус free tier — холодные старты/лимиты.

### GitHub Pages

- **Что это.** Бесплатный статический хостинг из ветки репозитория.
- **Зачем.** Фронтенд не требует сервера; Pages отдаёт `index.html`, JS и CSS.
- **Как здесь.** `gh-pages` публикует `dist`; `HashRouter` и `base: './'` обеспечивают работу в подпапке; `copy404` дублирует `index.html` в `404.html`.
- **Альтернативы.** Netlify/Vercel/Cloudflare Pages поддерживают SPA-fallback и удобнее, но GitHub Pages уже был в проекте и не требует отдельного аккаунта.

### `gh-pages`

- **Что это.** npm-пакет, который публикует папку в ветку `gh-pages`.
- **Зачем.** Автоматизировать деплой статики.
- **Как здесь.** `predeploy` собирает и копирует `404.html`, `deploy` пушит `dist`.
- **Альтернативы.** GitHub Actions — гибче, но сложнее; для учебного проекта скрипта достаточно.

### Reverse proxy и TLS

- **Что это.** Сервер (Nginx/Caddy/Traefik), который принимает HTTPS и проксирует запросы к приложению.
- **Зачем.** HTTPS, сжатие, лимиты, единый домен.
- **Как здесь.** На Render и GitHub Pages TLS предоставляется платформой. В локальном Docker TLS нет — это нормально для localhost.
- **Альтернативы.** Самоподписанные сертификаты неудобны; платформенный TLS проще.

## 7. Архитектурные подходы и паттерны

### REST

- **Что это.** Архитектурный стиль, где ресурсы адресуются URL, а действия — HTTP-методами (`GET`, `POST`, `PATCH`, `DELETE`).
- **Зачем.** Понятный контракт, кэширование GET, простота отладки.
- **Как здесь.** `/api/products`, `/api/products/:id`, `/api/cart/items/:id`; коды 200/201/204/400/401/403/404/409/429/500.
- **Альтернативы.** GraphQL даёт гибкие выборки, но сложнее кэшировать и защищать; gRPC быстрее, но неудобен для браузера. REST — оптимален для учебного магазина.

### Слоистая архитектура (routes → service → data)

- **Что это.** Разделение HTTP-слоя, бизнес-логики и доступа к данным.
- **Зачем.** Маршрут не должен знать, как считается скидка; сервис не должен знать про `reply`.
- **Как здесь.** `modules/*/routes.ts` — схемы и вызовы; `service.ts` — правила; `lib/prisma.ts` — БД; `lib/cache.ts` — кэш.
- **Альтернативы.** Вся логика в обработчике быстрее писать, но тяжело тестировать и переиспользовать. Слои разделяют ответственность.

### DTO (Data Transfer Object)

- **Что это.** Объект для передачи данных клиенту, отличный от модели БД.
- **Зачем.** Не отдавать внутренние поля и стабильно держать контракт.
- **Как здесь.** `toProductDto` преобразует Prisma-модель в `ProductDto`: `Decimal` → `number`, `Date` → ISO-строка, `images` → `image` + `images`. `serializeUser` убирает `passwordHash`.
- **Альтернативы.** Отдавать модель Prisma напрямую опасно (утечка полей) и неудобно (Decimal/Date). DTO — чистая граница.

### Dependency injection вручную

- **Что это.** Передача зависимостей в функцию/класс параметрами вместо создания внутри.
- **Зачем.** Тестируемость и явные связи.
- **Как здесь.** `registerUser(app, body)` получает `app` для подписи JWT; сервисы импортируют singleton `prisma`/`cache`. Полноценного DI-контейнера нет.
- **Альтернативы.** NestJS DI-контейнер мощен, но избыточен; ручная передача проще для размера проекта.

### Singleton

- **Что это.** Один экземпляр на процесс.
- **Зачем.** Не создавать десятки подключений к БД/Redis.
- **Как здесь.** `export const prisma`, `export const cache`, `transporter` в mailer.
- **Альтернативы.** Новый клиент на каждый запрос исчерпает пул. Singleton — стандарт для клиентов БД.

### Guard (защитник маршрута)

- **Что это.** Компонент/функция, которая не пускает дальше без условия.
- **Зачем.** Централизовать проверку авторизации.
- **Как здесь.** На сервере — `preHandler: authenticate/requireAdmin`; на клиенте — `RequireAuth`.
- **Альтернативы.** Проверки в каждом обработчике/странице дублируются. Guard — декларативно.

### Fail-fast конфигурация

- **Что это.** Приложение падает при старте, если конфиг неверен, а не через час в проде.
- **Зачем.** Раннее обнаружение ошибок.
- **Как здесь.** `env.ts` печатает список проблем и делает `process.exit(1)`, если нет `DATABASE_URL` или `JWT_SECRET` короче 16 символов.
- **Альтернативы.** Значения по умолчанию для секретов опасны. Лучше упасть сразу.

### Graceful shutdown

- **Что это.** Корректное завершение по `SIGTERM`/`SIGINT`.
- **Зачем.** Не оборвать запросы и закрыть соединения с БД/Redis.
- **Как здесь.** `server.ts` ловит сигналы, вызывает `app.close()`; хук `onClose` отключает Prisma и кэш.
- **Альтернативы.** `process.exit()` сразу может оставить незавершённые транзакции. Graceful shutdown — стандарт контейнеров.

### Pessimistic UI для серверных мутаций

- **Что это.** Сначала дождаться ответа сервера, потом обновить UI (в отличие от optimistic UI).
- **Зачем.** Сервер — источник истины по остаткам, скидкам и итогам; не показывать пользователю неверную сумму.
- **Как здесь.** `runServerMutation` ждёт ответ и только затем `setServerCart(cart)`. Для гостевой корзины обновление локальное и мгновенное.
- **Альтернативы.** Optimistic UI отзывчивее, но требует отката при ошибке. Для денег и остатков лучше дождаться сервера.

### Очередь мутаций

- **Что это.** Последовательное выполнение изменяющих запросов.
- **Зачем.** Быстрые клики «+» могут прийти в обратном порядке и перезаписать количество.
- **Как здесь.** `mutationQueue` в `CartProvider`: каждый запрос становится в цепочку `then`.
- **Альтернативы.** Параллельные запросы быстрее, но дают гонки. Очередь предсказуема.

### Идемпотентность и `upsert`

- **Что это.** Повторная операция не меняет результат неожиданно; `upsert` = insert или update по уникальному ключу.
- **Зачем.** Повторный запрос/ретрай не должен создавать дубликаты.
- **Как здесь.** `cartItem.upsert` по `(cartId, productId)`; `ensureCart` через `cart.upsert`; seed через `upsert`.
- **Альтернативы.** `create` + обработка ошибки уникальности сложнее и оставляет гонки. `upsert` атомарен.

### Soft-delete

- **Что это.** Вместо `DELETE` строка получает `deleted_at`.
- **Зачем.** Сохранить историю и не ломать ссылки; при этом скрыть товар из каталога.
- **Как здесь.** Все запросы каталога фильтруют `deletedAt: null`; удаление товара также чистит `cart_items` в транзакции.
- **Альтернативы.** Физическое удаление проще, но ломает FK (у товара `ON DELETE RESTRICT`) и историю. Soft-delete — компромисс.

### Пагинация на сервере

- **Что это.** Сервер отдаёт только одну страницу и общее количество.
- **Зачем.** Экономия трафика и памяти клиента.
- **Как здесь.** `page`, `limit`, `meta.total_items`, `meta.total_pages`.
- **Альтернативы.** «Загрузить всё и фильтровать в React» не масштабируется и противоречит ТЗ.

### Единый формат ошибок

- **Что это.** Все ошибки имеют вид `{ error: { code, message, details? } }`.
- **Зачем.** Клиент может обрабатывать `code` программно, а `message` показывать пользователю.
- **Как здесь.** `lib/errors.ts`: `AppError`, хелперы `badRequest`, `unauthorized`, `conflict`, обработчик Prisma-кодов (`P2002`, `P2025`, `P2003`).
- **Альтернативы.** Разные форматы у разных эндпоинтов усложняют клиент. Единый конверт — стандарт.

### Conventional Commits и Git Flow

- **Что это.** Соглашение о сообщениях коммитов (`feat:`, `fix:`, `chore:`) и модель ветвления (`master`, `develop`, `feature/*`).
- **Зачем.** История читается как changelog; стабильная ветка отделена от интеграционной.
- **Как здесь.** Ветки `feature/auth`, `feature/products-cache`, `feature/cart`; сообщения `feat(...)`, `merge: ...`, `release: ...`; даты 12–22.10.2026.
- **Альтернативы.** Trunk-based development быстрее для CI/CD, но Git Flow нагляднее для учебной демонстрации.

| Seed | Начальные данные |

| Инвалидация | Удаление устаревшего кэша |
| JWT | Подписанный токен с payload |

| RBAC | Доступ по ролям |
| Хэш | Необратимое преобразование данных |
| Соль | Случайная добавка к паролю перед хэшированием |
| Ротация токена | Замена старого refresh-токена новым |
| Отзыв токена | Пометка токена недействительным в БД |
| Soft-delete | Логическое удаление через дату |
| Транзакция | «Всё или ничего» |

| Graceful shutdown | Корректное завершение процесса |
| FSD | Слоистая архитектура фронтенда |

| Managed service | Сервис, которым управляет провайдер (БД, Redis) |
