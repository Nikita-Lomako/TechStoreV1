## Проект за 30 секунд

TechStore — интернет-магазин электроники. Пользователь открывает React-приложение, оно запрашивает данные у REST API на Fastify. API проверяет JWT, ходит в PostgreSQL через Prisma, а каталог дополнительно кэширует в Redis. Картинки товаров лежат в Supabase Storage. Всё упаковано в Docker; API можно запустить на Render, фронтенд — на GitHub Pages.

```text
Браузер
  │  React SPA (GitHub Pages или Vite)
  │  fetch + JSON + Bearer JWT
  ▼
Fastify API (Docker / Render)
  ├── Prisma ──────────► PostgreSQL (локально / Supabase)
  ├── ioredis ─────────► Redis (локально / Upstash)
  ├── fetch ───────────► Supabase Storage (картинки)
  └── nodemailer ──────► SMTP (письма о сбросе пароля)
```

## Главная мысль архитектуры

Каждый слой отвечает только за своё:

- **React-страницы** показывают интерфейс и не знают, как устроена БД.
- **API-клиент** на фронтенде централизованно добавляет токен, обновляет сессию и превращает HTTP-ошибки в понятные исключения.
- **Маршрут Fastify** описывает контракт: URL, схему тела, схему ответа, права доступа.
- **Сервис** содержит бизнес-правила: пароли, корзину, скидки, soft-delete, инвалидацию кэша.
- **Prisma** превращает вызовы TypeScript в параметризованный SQL.
- **PostgreSQL** хранит истину; **Redis** хранит только временную копию каталога.

Именно поэтому каталог можно кэшировать, не меняя логику страниц, а админку можно защитить и на клиенте, и на сервере независимо.

## Что нужно уметь объяснить своими словами

1. **Почему фронтенд и бэкенд разделены.** Фронтенд можно публиковать отдельно (GitHub Pages), API масштабировать отдельно (Render), а базу и хранилище отдать managed-сервисам.
2. **Почему каталог фильтруется в БД, а не в браузере.** Иначе пришлось бы загружать все товары, а пагинация и поиск работали бы медленно и неполно.
3. **Зачем Redis.** Повторные одинаковые запросы каталога не должны каждый раз считать `COUNT` и `SELECT`; кэш отдаёт готовый JSON за миллисекунды.
4. **Почему кэш всё равно безопасен.** У него короткий TTL (90 секунд), а любое изменение товара удаляет все ключи `products:`.
5. **Почему access-токен короткий, а refresh — долгий.** Если украдут access-токен, он быстро истечёт; refresh можно отозвать в БД и он хранится только в виде хэша.
6. **Почему пароль не хранится в открытом виде.** В БД лежит bcrypt-хэш; по нему нельзя восстановить пароль, а сравнение идёт медленно, что мешает перебору.
7. **Почему недостаточно скрыть админку на фронтенде.** Любой может вызвать API напрямую, поэтому `requireAdmin` проверяет роль на сервере.
8. **Почему soft-delete.** Товар исчезает из каталога, но исторические связи не ломаются; позиции корзины удаляются отдельно в транзакции.
9. **Что такое идемпотентность.** Повторный `upsert` или повторный merge не создаёт дубликаты: уникальный ключ `cart_id + product_id` и логика «сложить количества» это предотвращают.
10. **Почему Docker.** Одинаковое окружение локально и на сервере: один образ содержит Node, зависимости, Prisma Client и команду запуска.

## Термины, которые встречаются чаще всего

- **SPA** — Single Page Application: один HTML, дальше страницы рисует JavaScript.
- **REST API** — набор HTTP-ресурсов (`/api/products`, `/api/cart`), где метод HTTP выражает действие.
- **JWT** — подписанный токен с данными пользователя; сервер проверяет подпись, а не хранит сессию.
- **Refresh-токен** — долгоживущая случайная строка, по которой можно получить новый access-токен.
- **RBAC** — ролевое управление доступом (`customer` / `admin`).
- **ORM** — библиотека, которая связывает объекты языка с таблицами БД (здесь Prisma).
- **Миграция** — версионированное изменение схемы БД.
- **Seed** — наполнение БД демо-данными.
- **Кэш** — временное хранилище готовых ответов; источник истины всё равно БД.
- **TTL** — время жизни записи кэша.
- **Инвалидация** — удаление устаревших записей кэша.
- **Soft-delete** — «удаление» установкой даты в `deleted_at`, а не физическим `DELETE`.
- **DTO** — объект для передачи данных наружу, без лишних полей.
- **Middleware / hook** — код, который выполняется до или после обработчика запроса.
- **CORS** — правила, какие сайты могут обращаться к API из браузера.
- **Rate limit** — ограничение количества запросов за период.
- **Graceful shutdown** — корректное завершение: перестать принимать запросы, закрыть БД и Redis.
- **Multi-stage build** — несколько этапов Dockerfile, чтобы в финальный образ не попали инструменты сборки.
- **Feature-Sliced Design (FSD)** — разбиение фронтенда по слоям и бизнес-смыслам.

## Рассказ на 2 минуты

> Это full-stack интернет-магазин. Фронтенд на React и Vite показывает каталог, карточку, корзину и админку; он общается с REST API на Fastify. API валидирует запросы схемами TypeBox, проверяет JWT и роли, а бизнес-логику держит в сервисах. Данные лежат в PostgreSQL, доступ — через Prisma с миграциями и seed. Каталог кэшируется в Redis по нормализованному ключу с TTL 90 секунд; любое изменение товара сбрасывает все ключи `products:`. Пароли хранятся в bcrypt, access-токен живёт 15 минут, refresh — 7 дней, ротируется и лежит в БД как SHA-256-хэш. Админские маршруты защищены `requireAdmin` на сервере, а не только скрытием кнопки. Картинки загружаются в Supabase Storage через сервер, service-role key не попадает в браузер. Всё упаковано в multi-stage Docker-образ, работает от пользователя `node`, есть healthcheck и graceful shutdown. Локально стек поднимается `docker compose up --build`; в облаке развёрнуты Supabase, Upstash, Render и GitHub Pages — пошаговая инструкция есть в документации.

## Как поддерживать документацию

Если меняется поведение API, схема БД, переменная окружения или команда запуска — обновите:

1. `README.md` (краткая инструкция),
2. соответствующий файл в `docs/`,
3. при необходимости — Swagger-схему в коде (она является машинным контрактом).

Документация описывает **текущее состояние репозитория**, а не гипотетическую версию. Облачный деплой выполнен: API на Render, PostgreSQL и Storage в Supabase, Redis в Upstash, фронтенд на GitHub Pages. Инструкция в [`06-DEPLOYMENT.md`](./06-DEPLOYMENT.md) позволяет повторить его с нуля.
