# 04. Безопасность сайта и данных

Этот файл отвечает на три вопроса:

1. От чего мы защищаемся?
2. Что конкретно сделано в коде?
3. Какие риски остаются и что делать дальше?

Важно: безопасность — не одна кнопка, а набор слоёв. Если один слой ошибётся, следующий должен остановить атаку. Это называется **defense in depth** (эшелонированная защита).

---

## 1. Что защищаем

| Актив | Почему важен | Где хранится |
| --- | --- | --- |
| Пароли | Компрометация даёт доступ к аккаунту | Только bcrypt-хэш в `users.password_hash` |
| Refresh-токены | Позволяют получать новые access-токены | SHA-256 хэш в `refresh_tokens` |
| Reset-токены | Позволяют сменить пароль | SHA-256 хэш в `password_reset_tokens` |
| JWT-секрет | Позволяет подделать любой access-токен | Переменная `JWT_SECRET` |
| Данные пользователей | Email, корзина, история | PostgreSQL |
| Админ-функции | Изменение каталога и цен | API + RBAC |
| Service-role key Supabase | Полный доступ к Storage | Только env на сервере |
| Файлы товаров | Подмена картинок/вредоносный контент | Supabase Storage |
| Доступность API | Перебор паролей, спам, перегрузка | Rate limit, лимиты тела |

## 2. Модель угроз (упрощённо)

| Угроза | Пример | Основные меры | Остаточный риск |
| --- | --- | --- | --- |
| Кража пароля из БД | Утечка дампа | bcrypt + соль, 12 раундов | Слабые пароли всё равно подбираются |
| Перебор паролей | Бот пробует тысячи комбинаций | Rate limit 10/15 мин на login, общий 200/мин | Распределённый бот с многих IP |
| Подделка токена | Изменение payload JWT | Подпись HS256 секретом | Утечка `JWT_SECRET` |
| Кража access-токена | XSS/чужое устройство | Короткий срок 15 минут | До истечения токен действует |
| Кража refresh-токена | XSS/локальное хранилище | Ротация, отзыв, хэш в БД | Нет обнаружения повторного использования семейства |
| Повышение привилегий | `customer` вызывает admin API | `requireAdmin` на сервере | Ошибка в новом маршруте без preHandler |
| SQL-инъекция | `' OR 1=1 --` в поиске | Prisma parameterized queries | Сырой SQL без параметров |
| XSS | Вредоносный скрипт в данных | React экранирует, нет `dangerouslySetInnerHTML` | Токены в localStorage |
| CSRF | Чужой сайт шлёт запрос от имени пользователя | Нет cookie-аутентификации, Bearer вручную | Если перейти на cookies — понадобится CSRF-токен |
| Подделка файла | Загрузка `.html`/скрипта | MIME-allowlist, размер, случайное имя | MIME можно подделать; нет проверки magic bytes |
| Утечка секретов | `.env` в Git | `.gitignore`, примеры без секретов | Секрет может попасть в лог/скриншот |
| DoS | Гигантский JSON/файл | `bodyLimit` 1 МБ, upload 5 МБ, rate limit | Сетевой DDoS — задача провайдера |
| Enumeration | Узнать, есть ли email | Одинаковые ответы login/forgot | Регистрация всё равно сообщает о занятом email |

## 3. Аутентификация: кто ты

### 3.1. Пароли

**Что сделано:**

- Пароль принимается только на регистрации/входе/сбросе, минимум 8 символов, максимум 72.
- Хранится `bcrypt.hash(password, 12)`.
- Сравнение — `bcrypt.compare`, которое использует соль из хэша.
- В API-ответах пароль и хэш не возвращаются: `serializeUser` и схемы ответа.
- В логах пароль не пишется.

**Почему bcrypt, а не SHA-256.** SHA-256 быстрый: миллиарды попыток в секунду на GPU. bcrypt намеренно медленный и имеет соль, поэтому перебор дорог. 12 раундов — компромисс между безопасностью и временем входа (примерно сотни миллисекунд).

**Почему максимум 72.** bcrypt игнорирует байты после 72-го; ограничение делает поведение предсказуемым.

**Что можно улучшить.** Проверять пароль по списку утечек (Have I Been Pwned), добавить требования к сложности, Argon2id.

### 3.2. Access-токен (JWT)

- Payload: `{ sub: userId, email, role }`.
- Срок: 15 минут (`JWT_EXPIRES_IN`).
- Подпись: HS256 секретом `JWT_SECRET` (минимум 16 символов, рекомендуется 32+).
- Передаётся в `Authorization: Bearer <token>`.
- Проверяется `request.jwtVerify()` в `authenticate`.

**Почему короткий срок.** JWT нельзя отозвать до истечения без дополнительного хранилища. 15 минут ограничивают окно атаки.

**Почему в payload есть роль.** `requireAdmin` может проверить её без запроса в БД. Минус: если роль изменили, старый токен ещё 15 минут будет считать по-старому. Для учебного проекта приемлемо; в строгих системах роль проверяют в БД или отзывают токены.

**Что не кладём в JWT.** Пароль, персональные данные, секреты. Payload не шифруется, его может прочитать любой, у кого есть токен.

### 3.3. Refresh-токен

- 32 случайных байта (`randomBytes(32)`), base64url.
- В БД — только `SHA-256`.
- Срок 7 дней.
- Ротация при каждом `/api/auth/refresh`: старый помечается `revokedAt`, новый создаётся.
- При сбросе пароля все активные refresh-токены пользователя отзываются.
- При выходе текущий refresh отзывается.

**Почему opaque, а не JWT.** Нужна возможность мгновенного отзыва и ротации. Случайная строка не раскрывает данные и проверяется по БД.

**Почему SHA-256, а не bcrypt.** Токен уже имеет 256 бит случайности, перебирать его бессмысленно. Быстрый хэш достаточен и не замедляет refresh.

**Остаточный риск.** Если украденный refresh используется раньше владельца, сервер не отличит его от легитимного. Продвинутое решение — «token family» и автоматический отзыв всей цепочки при повторном использовании старого токена.

### 3.4. Где хранятся токены на клиенте

`localStorage`: `techstore.auth.access`, `techstore.auth.refresh`.

**Плюсы:** просто, явный `Authorization`-заголовок, нет CSRF через cookie.

**Минусы:** любой XSS может прочитать токены. Поэтому:

- React экранирует значения по умолчанию;
- в проекте нет `dangerouslySetInnerHTML` в React-коде;
- сторонние скрипты не подключены;
- access живёт 15 минут, refresh можно отозвать.

**Альтернатива для продакшена:** refresh в `httpOnly; Secure; SameSite=Strict` cookie, access — в памяти. Тогда XSS не прочитает refresh, но понадобится CSRF-защита и настройка CORS с `credentials: true`. Это более безопасно, но сложнее; текущий вариант — осознанный компромисс для учебного SPA на GitHub Pages.

### 3.5. Восстановление пароля

- Сырой токен — 32 случайных байта.
- В БД — SHA-256, срок 15 минут, `usedAt` для одноразовости.
- Запрос всегда отвечает `202` и одинаковым текстом, даже если email не существует.
- Новый запрос гасит все предыдущие неиспользованные reset-токены.
- После смены пароля все refresh-сессии отзываются.
- Страницы `/forgot-password` и `/reset-password` отдаются с `Cache-Control: no-store`.
- `EXPOSE_RESET_TOKEN` по умолчанию `false`; в `server/.env.example` стоит `true` **только для локальной отладки**. В продакшене включать нельзя.
- Если SMTP не настроен, ссылка пишется в лог. Это удобно локально, но в продакшене лог с токеном — чувствительные данные. Настройте SMTP.

**Почему не отправлять токен в ответе всегда.** Это позволило бы любому запросить сброс и сразу сменить пароль, зная только email.

## 4. Авторизация: что тебе можно

### 4.1. RBAC на сервере

```ts
export async function requireAdmin(request, reply) {
  await authenticate(request, reply)
  if (request.user.role !== 'admin') {
    throw forbidden('This action requires the admin role')
  }
}
```

Защищены:

- `POST /api/products`;
- `PATCH /api/products/:id`;
- `DELETE /api/products/:id`;
- `POST /api/uploads`.

Корзина защищена `authenticate`: пользователь видит только свою корзину, потому что запросы фильтруются по `request.user.sub`.

### 4.2. Почему клиентского guard недостаточно

`RequireAuth adminOnly` скрывает страницу, но любой может открыть DevTools, вызвать `fetch('/api/products', { method: 'POST' })` или использовать curl. Поэтому **каждый** админский маршрут имеет `preHandler: requireAdmin`. Клиентский guard — только UX.

### 4.3. Владение ресурсом

В корзине недостаточно проверить, что пользователь авторизован. Нужно убедиться, что позиция принадлежит **его** корзине:

```ts
prisma.cartItem.findFirst({ where: { id: itemId, cart: { userId } } })
```

Иначе пользователь A мог бы изменить позицию пользователя B, зная UUID. Это называется **IDOR** (Insecure Direct Object Reference); здесь он закрыт фильтром по `userId`.

## 5. Валидация и целостность

### 5.1. Валидация на границе

Все входные данные проверяются TypeBox-схемами:

- `email` — формат email, максимум 320;
- `password` — 8..72;
- `quantity` — 1..99;
- `images` — минимум 3, максимум 12;
- `price` — 0..100 000 000;
- `rating` — 0..5;
- `page` — 1..100 000;
- `limit` — 1..100.

Fastify возвращает `400 VALIDATION_ERROR` с путём и сообщением. Внутренний код может доверять типам.

### 5.2. Сериализация ответа

Схемы ответов — это «белый список» полей. Даже если из сервиса случайно вернуть объект с `passwordHash`, Fastify оставит только описанные поля. Это защита от утечки.

### 5.3. Ограничения БД

- `UNIQUE(email)` — два аккаунта с одним email невозможны.
- `UNIQUE(token_hash)` — токены не дублируются.
- `UNIQUE(cart_id, product_id)` — одна позиция на товар.
- `FOREIGN KEY` — нельзя создать корзину для несуществующего пользователя.
- `ON DELETE CASCADE` для корзины/токенов и `RESTRICT` для товара — предсказуемое поведение.
- `Decimal(10,2)` — деньги без плавающей точки.

### 5.4. Транзакции

Критичные изменения атомарны:

- выдача refresh-токена (удалить старые + создать новый);
- ротация refresh;
- сброс пароля (пароль + погашение токена + отзыв сессий);
- удаление товара (позиции корзин + soft-delete);
- merge корзины.

Это не даёт данным остаться в полусостоянии при ошибке.

### 5.5. SQL-инъекции

Prisma передаёт значения параметрами, а не склеивает строки. Например, `contains: query.search` превращается в параметризованный `ILIKE $1`, поэтому кавычки и `--` не ломают запрос.

Единственный `$queryRaw` — категории:

```ts
prisma.$queryRaw(Prisma.sql`
  SELECT category AS name, COUNT(*)::int AS count, ...
  FROM products
  WHERE deleted_at IS NULL ...
`)
```

Здесь нет пользовательских значений. Если будете добавлять raw SQL, всегда используйте `Prisma.sql` с параметрами, а не шаблонную строку.

## 6. Браузерная безопасность

### 6.1. CORS

Разрешены только origin из `CORS_ORIGINS`:

```env
CORS_ORIGINS=http://localhost:5173,http://localhost:4173,https://nikita-lomako.github.io
```

- Запросы без `Origin` (curl, server-to-server) разрешены: они не браузерные.
- `credentials: false` — куки не отправляются.
- Разрешены только `Content-Type` и `Authorization`.
- `X-Cache` и `X-Cache-TTL` доступны JS.

**Почему не `*`.** С `Authorization` и потенциальными будущими куки `*` опасен. Allowlist точнее.

**Что CORS не делает.** Он не защищает API от curl/ботов. Авторизация и rate limit — отдельные слои.

### 6.2. Helmet

Выставляются заголовки:

- `X-Content-Type-Options: nosniff` — браузер не угадывает MIME;
- `X-Frame-Options` — защита от встраивания в iframe (кликджекинг);
- `Referrer-Policy: no-referrer` — не утекает URL;
- `Strict-Transport-Security` — на HTTPS;
- другие стандартные заголовки.

**CSP отключён глобально**, потому что Swagger UI использует inline-скрипты. Для `/docs` включён отдельный `staticCSP: true`. Если в продакшене выключить Swagger (`SWAGGER_ENABLED=false`), глобальный CSP можно включить — это дополнительно усилит защиту от XSS.

### 6.3. XSS

- React экранирует текст в JSX: `<p>{product.title}</p>` безопасно.
- Нет `dangerouslySetInnerHTML` в React-компонентах.
- Нет подключения сторонних скриптов/аналитики.
- HTML-страницы сброса пароля используют `innerHTML` только для ссылки, собранной из токена и `encodeURIComponent`; это локальная dev-функция.

**Главный остаточный риск** — токены в `localStorage`. Если появится XSS, он сможет их прочитать. Меры: не добавлять недоверенный HTML, включить CSP, перейти на httpOnly-cookie для refresh.

### 6.4. CSRF

CSRF возможен, когда браузер автоматически прикладывает cookie к запросу с чужого сайта. Здесь аутентификация идёт через `Authorization`, который автоматически не прикладывается. Поэтому классический CSRF сценарий не работает.

Если перейдёте на cookie, обязательно добавьте:

- `SameSite=Strict/Lax`;
- CSRF-токен или double-submit cookie;
- проверку `Origin`.

### 6.5. Кликджекинг

Helmet по умолчанию ставит `X-Frame-Options: SAMEORIGIN`. Дополнительно можно включить CSP `frame-ancestors 'none'`.

## 7. Ограничение злоупотреблений

### 7.1. Rate limit

| Маршрут | Лимит |
| --- | --- |
| Все запросы | 200/мин на IP |
| `POST /api/auth/register` | 5/15 мин |
| `POST /api/auth/login` | 10/15 мин |
| `POST /api/auth/refresh` | 30/15 мин |
| `POST /api/auth/logout` | 30/15 мин |
| `POST /api/auth/forgot-password` | 5/15 мин |
| `POST /api/auth/reset-password` | 10/15 мин |

**Ограничение.** Хранилище лимитера — память инстанса. При нескольких репликах у каждой свой счётчик. Для строгого лимита нужен Redis-store или WAF.

### 7.2. Лимиты размера

- JSON body: 1 МБ.
- Upload: 5 МБ, один файл, не более 10 полей.
- `quantity`: максимум 99.
- `images`: максимум 12.

Это защищает от случайного и намеренного раздувания запросов.

### 7.3. Таймауты

- Redis connect timeout 2 секунды, максимум 3 попытки.
- Prisma использует свои таймауты пула.
- HTTP-сервер полагается на таймауты платформы (Render).

## 8. Секреты и инфраструктура

### 8.1. Переменные окружения

- Реальные `.env` в `.gitignore`.
- В репозитории только `.env.example` с заглушками.
- `JWT_SECRET` обязан быть минимум 16 символов; лучше 32+ случайных.
- `SUPABASE_SERVICE_ROLE_KEY` никогда не попадает в клиентский бандл: он используется только в `server/src/modules/uploads/routes.ts`.
- `VITE_*` переменные публичны по определению — там не должно быть секретов.

### 8.2. Docker

- Multi-stage: в runtime нет TypeScript и dev-зависимостей.
- `USER node`: процесс не root.
- Только необходимые файлы.
- Healthcheck и graceful shutdown.
- `.dockerignore` исключает `.env`, `node_modules`, тесты, `.git`.

**Почему non-root важен.** Если злоумышленник получит выполнение кода в контейнере, root облегчит эскалацию и доступ к volume.

### 8.3. База данных

- Отдельный пользователь БД с паролем, не суперпользователь.
- В облаке — SSL (`sslmode=require`, если провайдер требует).
- Миграции применяются контролируемо (`migrate deploy`), а не `db push`.
- Регулярные бэкапы (Supabase делает их на платных тарифах; проверьте свой план).
- Принцип наименьших привилегий: приложению не нужны права создавать других пользователей БД.

### 8.4. Supabase Storage

- Bucket `product-images` публичный: картинки доступны по URL без авторизации. Для товаров это нормально, но **не загружайте туда секреты/личные файлы**.
- Загрузка только через API и только админом.
- MIME-allowlist: JPEG, PNG, WebP, AVIF, GIF.
- Случайное имя объекта.
- Service-role key обходит RLS, поэтому хранится только на сервере.

**Остаточный риск.** MIME-тип приходит от клиента и может быть подделан. Полноценная защита — проверять сигнатуру файла (magic bytes) и/или перекодировать изображение на сервере. Для учебного проекта достаточно allowlist + админского доступа, но это стоит знать.

## 9. Логи и приватность

- Fastify по умолчанию логирует метод, URL, статус, время, IP (при `trustProxy`), но **не тело** запроса.
- Пароли и токены не логируются.
- Исключение: при отсутствии SMTP ссылка сброса с токеном пишется в `console.info`. Это допустимо локально, но в продакшене настройте SMTP или отключите такой вывод.
- Ошибки 500 логируются с `err`, но клиенту в production отдаётся общая фраза.
- Ошибки Supabase Storage логируются со статусом и текстом ответа; секрет туда не попадает.

Подробнее — в `05-LOGGING.md`.

- [ ] Supabase service-role key не в клиенте и не в Git.

- [ ] HTTPS включён (Render/Pages дают его автоматически).

- [ ] Бэкапы БД и проверка восстановления.

## 11. Как объяснить безопасность за 2 минуты

> Пароли хранятся только в виде bcrypt-хэша. После входа сервер выдаёт короткий JWT на 15 минут и долгий refresh-токен, который лежит в БД в виде SHA-256-хэша и ротируется. Access-токен проверяется на каждом защищённом маршруте, роль проверяется отдельно: `customer` не может вызвать админский API, даже если откроет DevTools. Все входные данные валидируются схемами, Prisma параметризует SQL, а схемы ответов не дают утечь лишним полям. CORS разрешает только наш фронтенд, Helmet добавляет защитные заголовки, rate limit ограничивает перебор. Сброс пароля — одноразовая ссылка на 15 минут, хранится как хэш, после смены пароля старые сессии отзываются. Секреты лежат в env, контейнер работает не от root. Остаточные риски: токены в localStorage при XSS, rate limit в памяти и публичный bucket для картинок — они описаны и имеют план усиления.
